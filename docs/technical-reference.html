The road to 1.0

After the audit the core does what this document says, the tests cover the paths that keep servers up (the failure count, the backoff ladder, the restart budget through the real manager, the watchdog from its real inputs, the keepalive, self-update and its rollback), and the live server's exported logs replay through the real watchdog with every real dead stretch restarted and nothing on the healthy ones. What stands between this and a 1.0 a host can leave alone is, in order:

1. It has never run the live server

Every claim about uptime comes from replaying exported logs and from test servers with nobody on them. The post-game death (13 times with its roster-loss line in the exported logs at 90 or more players, more on older versions that don't print the line), the keepalive, no_joins, Vergil's strike ladder and mutes, and the relay have not acted on a real 100-player server. 1.0 should mean proven on the job, which only a burn-in on the live host can give. Suggested exit criteria for two weeks:

  • every post-game death recovered by the watchdog within 3 minutes of the match report;
  • no restart nobody can explain (each one is in logs/huragok.log with its reason);
  • no FAULTED that needed a person, no Huragok crash (the start loop logs any restart of itself), no part switched off;
  • logs/window.log read once a week for anything confusing.

  • Mutes from !mute or the console still end when the server restarts; only Vergil's own are kept.

What it is and why it exists

Huragok is one Python program that runs every Project Reclaimer (Halo 3 MCC) dedicated server on a machine, keeps them up, and gives the host and moderators one place to control them. It sits beside the server program, not inside it: it never patches the game. It is named for Halo 3: ODST's Engineer, and its three named parts are described under The three parts.

The problems it answers

  • Servers die and stay dead. On the live server, a game ends, every player drops at once ("Host roster lost 112 of 112 players"), and nobody can join again. The server program's own internal supervisor only restarts after five minutes without frames, so the server sits empty.
  • Moderation is by hand. The host watches chat and bans manually, cannot play, and is burning out. Voice abuse is the core problem; text filtering only covers chat and names.
  • Running several servers is fiddly. Each server is a folder with its own config, ports, RCON password, playlists and Workshop items. Setting one up, updating the server program and changing settings all meant editing files and running commands by hand.

What it does, in one list

  • Starts each server, restarts it after a crash with backoff, and gives up (FAULTED) rather than thrashing. Starts itself again when it crashes, and takes a new version of itself that won't start back out.
  • Watches for a dead, stuck, unjoinable or hung server and restarts it, after the game where possible.
  • Warns players in chat before any planned restart or stop, and skips the warning when nobody is on.
  • Acts on listed words in chat (automod): each strike is the next step on its line, kicks, then mutes, then a ban. Kicks a name with a listed word, or a banned name, every time it joins until it changes.
  • Gives chosen players in-game ! commands by role (everyone, member, moderator, admin, owner), keyed by player ID, and keeps everyone listed safe from votes to kick.
  • Records every player seen and every warn, mute, kick and ban, with who did it and why, in SQLite.
  • Sets up new servers from packages, edits playlists, Workshop items and settings (each file change checked before the file is replaced), and installs new versions of the server program and of Workshop mods after games.
  • Relays the official RCON client for remote moderators, each with their own password and role.

Design principles

These rules explain most of the code. Changes should keep them or replace them on purpose.

  1. A server never depends on Huragok's process. Each server runs in its own process group (Windows) or session (Linux) with output to a file. Closing the window leaves servers running; reopening adopts them.
  2. Up means RCON answers. A process existing is not enough; a server is ready only when its remote console replies.
  3. Use what the server offers. Talk to it through RCON, its files (server.log, status.json) and its own dedicated commands. No memory reading, no patching.
  4. Nothing in a manager waits. Each server is a state machine ticked once a second; a stop in progress is a task the next tick checks. The window never blocks the servers: what it shows goes out from a thread of its own, and slow work (the program's commands, file scans, port probes) runs in worker threads.
  5. Restart after the game, not in the middle of it, unless the server is already broken for everyone.
  6. Give up instead of looping. Repeated fast failures or too many restarts in an hour stop automatic restarts and ask a person.
  7. Every action on a player goes through one ledger, so it is recorded, shows who acted, and respects dry run. A moderation command is never resent after an error, because it may already have run.
  8. Never hammer a refused RCON password. Five failures in ten minutes lock every tool on the machine out of that server, so a refused password is tried again only when the server's files give a different one, once after the server restarts (never more than 2 refusals in 10 minutes), or else every 10 minutes.
  9. The host's files are theirs, and keep up with Huragok. First start writes settings.toml, commands.toml, automod.txt and names.txt; updates replace only the program, and the new version brings those files up to date as it starts (a step per change, each run once, each file backed up first) without taking away anything the host wrote; an edit Huragok makes to a host's file changes exactly what was asked or leaves the file as it was. No release needs a clean install.
  10. Same behaviour on Windows and Linux, with the platform differences kept in the process backend and the keyboard layer.

Goals, scope and non-goals

Huragok serves three goals. Keep servers up with nobody watching: the Superintendent's restarts, watchdog and keepalive. Faster moderation, voice abuse being the core problem: Vergil's automod, in-game commands and relay. One place to set up and manage servers: Huragok's own new servers, content, Workshop, updates and settings. 1.0 means a host can leave it alone; what still stands in the way is in The road to 1.0.

Non-goals

  • Patching, replacing or reading the memory of the server program.
  • Replacing the built-in supervisor inside dedicated run; it is wrapped, one dedicated per server.
  • Detecting voice abuse automatically, or a shadow mute: the server offers neither.
  • Several machines sharing state: there is one SQLite database per machine.
  • Third-party plugins: parts ship together, and new work comes as a pull request.
  • A web panel or HTTP API (listed as later).
  • A bundled Python: the host installs Python 3.11 or newer.

Architecture

Huragok is one Python process running one asyncio event loop. Everything it learns becomes an event on one in-memory bus, and everything it does to a server goes through that server's state machine in the Fleet.

Read it left to right: server signals are read into events, the bus fans them out, and the parts and keepalive ask the Fleet to restart; the window and start.cmd ask the Fleet too, which alone tells the backend to start or stop a process.

The four layers

  1. Readers turn each server's signals into events: RconClient (the WebSocket console), FileWatcher (server.log and status.json) and the process backend (the dedicated console output file).
  2. The bus (EventBus, events.py) delivers each event synchronously to every subscriber whose pattern matches (rcon.chat, rcon.*, *). Subscribers must not block.
  3. Deciders act on events and timers: StateTracker keeps the live picture, the Fleet ticks one ServerManager per server, Keepalive checks for hangs, and the parts (commands, automod, watchdog, eventlog) each run behind their own queue.
  4. Surfaces only ask: the window (menu.py), start.cmd verbs (through files in records/requests/), the relay for remote moderators, and the second window (reading records/live.json). None of them change a server directly; they call Fleet verbs.

How failures are contained

  • Huragok itself runs under the start loop, a small parent process on the old code: a crash is started again after 5, 15, 30, 60 s, then every 5 minutes (D18). The servers never notice.
  • Every core loop is started through Supervisor._spawn: an exception is logged ("… failed; restarting it in 5 s") and the loop restarts after 5 s: the fleet, each RCON client and file watcher, the state tracker, the keepalive, the server-folder and file checks, the Workshop updates, the relay. Not restarted: Huragok's own update checks, the server program's, the window, the part runners (they contain their own failures) and the relaunch onto a new version.
  • A bus listener that raises is logged; the other listeners still get the event.
  • Each part has its own queue (1,000 events) and a time limit per handler of max(handler_timeout, [rcon] command_timeout + 5) (15 s by default), so an RCON call times out first. 5 failures in 10 minutes switch the part off for 10 minutes (supervisor.part_disabled), then it is on again (supervisor.part_enabled, D22); an RCON error in a handler (a slow or restarting server) is logged, not counted; a part whose setup failed stays off. Other parts carry on.
  • A ServerManager step that raises is logged at most once a minute ("manager error (server untouched): …"); the server is left as it is and the rest of the Fleet carries on. A request from outside that can't be read is answered "not understood: …" and the fleet loop carries on.
  • The per-server state refresh loops are started with plain asyncio.ensure_future, not _spawn, so each one catches its own errors: a reply it can't use is logged ("couldn't read the server's state") and the loop goes on. Until 0.2.2 one ended silently on its first run. Every test now fails if asyncio logs a task that failed with nobody looking.

Clocks

  • Monotonic clock for every interval (D25): phase times, backoff, countdowns, plan ages, the live file's throttle, log-message throttling, the last good RCON reply, the keepalive's runs and retries, part failure windows and cool-downs, PortWatch, the relaunch wait, the start loop's run length.   • Wall clock (time.time) for anything saved or compared across runs or with the server: the hourly restart budget (restart_times), history, uptime and the start time, the daily date and slot, event times, status.json's age (its own updated), request times.
  • An RCON event carries the server's own time; other events take the local time when they are made.
  • The daily restart uses local time and fires once per date. The slot is compared as an instant, not a clock reading, so a slot inside the hour the clocks skip still fires, and in the repeated hour only the first one does.

How servers are found

  • Every folder in SERVERS/ that holds a dedicated.toml is read; folders starting with . or _ are ignored (they are set aside or still being made). server_folder adds one more folder (the 0.1 layout). Discovery repeats every 10 s while running.
  • Each enabled [[server]] block is one server. Its name gives the slug (LG Test Server becomes lg-test-server; a name with no a-z or 0-9 gets server-<8 hex>). Two names with one slug ("LG Slayer" and "LG-Slayer") would share their records, console log and FAULTED report, so the later folder is left out until one is renamed ("… would share their records and logs: Huragok names both lg-slayer …"); a running server keeps its slug, and new and rename refuse such a name.
  • Its data folder is, in order: [[server]] data in settings.toml; the data/*/instance.json whose name matches; data/<slug>.
  • RCON is read fresh on every connect: instance.json's rcon block wins over dedicated.toml's [rcon]. The RCON port is the game port unless set. 0.0.0.0 becomes 127.0.0.1.
  • Checks: names must be unique (the copy in a folder not named after the server is left out); ports must be unique (the second server gets an error); RCON must have a password, or the server shows CONFIG ERROR and is never started. A [[server]] block in settings.toml for a server servers = [...] leaves out is not a problem.
  • A folder that cannot be read is left out alone, named in red on the dashboard; every other server keeps running. A running server whose folder disappears is kept until it stops.

Hosts' files across updates

Every install since 0.4.0 counts as live: an update goes over it, and no release may need a clean install. An update replaces the program only, so a host's settings.toml is the one their first start wrote. Since 0.4.1 migrate.py keeps it in step: as Huragok starts (in its own process, under its lock, before any server is looked after) it runs each step not yet done, and check lists what the next start would change.

  • A step is keyed <version>/<what> and runs once (records/files.json lists those done). It looks before it changes anything, changes TOML only through tomledit (add_table_key, comment_out_table_key, replace_comments), and copies the file to records/previous-files/<version>/ before its first change. It adds what's missing, turns what does nothing into a comment saying why, and swaps only comment blocks that are exactly what an earlier version wrote: the host's values and comments stay. A step that fails, or a file that can't be read, is logged and tried again at the next start; Huragok starts regardless, reading the old form.
  • 0.4.4's step: [process] priority = "high" added after stop_servers_on_exit, with the template's comment saying what each choice does; only where the file has a [process] table (or 0.1's [windows]), and never over a # priority = … the host wrote. Without the line the default is High anyway.
  • 0.4.2's steps: [updates] install_on_server_restart becomes auto_update (true carried over with the old line left as a comment saying so, false replaced), and the [updates] comment that says the window keeps saying a new version is out.

Server lifecycle

Keeping the servers running is the Superintendent's part (SUPT). Each server is a ServerManager state machine ticked once a second. With the process backend, each server runs as its own detached dedicated run process, so servers outlive Huragok and are adopted when it comes back.

Two layers of supervision

project-reclaimer.exe dedicated run is itself a supervisor: it runs the game and restarts it when the game crashes, hangs or returns to MCC's menus. The Superintendent runs dedicated run and watches both layers.

  • A game crash inside dedicated does not end the dedicated process. The Superintendent sees it only as console lines: server.crashed (with a kind: hang, menus, error, panic, engine_exit, other) and then server.started with the new game pid.
  • The Superintendent's own crash handling (backoff, FAULTED) applies when dedicated itself exits.
  • The built-in layer waits five minutes without frames before acting on a hang. That gap is why the watchdog and keepalive exist.

From double-click to running

  1. start.cmd finds Python 3.11+ (by its exit code, so a path with accents, Cyrillic or CJK letters works), makes engine/.venv (again, when its Python is gone), installs requirements.txt when it changed, checks that import huragok, psutil, websockets works (installing the packages again if not), and runs python -m huragok start --hold.
  2. On the very first start it prints the banner and the title HURAGOK <version>: THE FIRST DROP, writes settings.toml, commands.toml, automod.txt, names.txt and the starter packages, then exits with code 3 so the host reads them first. Every later start writes back any of those files that was deleted.
  3. If Huragok already runs from this folder, a second window opens instead (with --no-menu: "Huragok is already running from this folder (process N)", exit code 4). The lock is records/huragok.pid, checked by pid and process start time; 0.2.1's records/supervisor.pid counts too. The second window draws records/live.json, sends its keys through records/requests/, and takes over when the first window closes.
  4. Otherwise the start loop takes the lock and starts the real Huragok as a child (start --child), which takes the lock over and hands it back as it exits; the start loop holds it in between, so nothing steps into the gap. The start loop stays on the old code and does as little as possible (D18): exit code 10 (a self-update installed a new version) starts the new version; a new version that ends within 2 minutes is put back; 0, 3 and 4 end the loop; a settings problem (2) ends it, or with --no-menu is tried again every 5 minutes or as soon as settings.toml changes; anything else is a crash: "Huragok stopped unexpectedly (exit code 1); starting it again in 5 s. logs/huragok.log says why.", then 15, 30 and 60 s, then every 5 minutes, the count starting over once a run lasted 10 minutes. A request from start.cmd (a stop, say) made during that wait starts Huragok at once to answer it. The start loop's lines go to huragok.log as launcher: … and to the window.
  5. The child loads settings, takes the lock and starts its loops. The Fleet boots: the backend re-adopts the processes in running-servers.json (same pid and same start time), and each manager sets wanted from autostart.

Phases

Three phases are left out of the drawing. preparing sits between launch and booting: jobs that need the server stopped run first (a Workshop mod's new version swapped in, the server program replaced, an old .exe.old removed). They are the snapshot taken as it begins; each has 20 minutes (JOB_LIMIT); one that fails or runs out of time is logged ("… took longer than 20m 00s; starting it anyway") and the server starts whatever they did (D24). A job added meanwhile waits for the next start. X during preparing calls the jobs off (what they hadn't finished runs at the next start) and the server stays stopped. restarting: a command backend that only has a restart command runs it; a stop asked for meanwhile is honoured once it returns. offline: the backend can't start servers (attach) and the server isn't reachable.

A server seen alive in backoff or faulted is adopted straight into running; in idle or offline it is adopted when the backend can restart it, and is external otherwise, or when (process backend) something else listens on its RCON port. A stop that doesn't end the process (the Ctrl+Break helper fails or times out, and the process outlives the kill) goes back to running: the server stays Huragok's (kept in running-servers.json), shows "! couldn't stop it: …", the log names the process to end by hand, and no restart is reported; after a stop of every server, Huragok's log names the one left running.

The rules each manager follows

  • Up means RCON answers. booting becomes running when RCON signs in (or refuses the password: "up, but its console can't be used: …"). No answer within ready_seconds (300 s) is a failed start, and the process is ended (for docker and command, the stop command runs only when the server shows no sign of life).
  • Crashes back off. The process exiting on its own is a crash. Restarts wait 5, 10, 30, 60, then 300 s (backoff_seconds). Dying within good_run_seconds (600 s) of a start counts as a failed start; running longer resets the count.
  • Pause after 5. max_failures (5) failed starts in a row mean FAULTED: no more tries for now. After faulted_retry_minutes (30, then 60, the last repeating) the Superintendent tries once more (event server.fault_retry): fail_count is set one short of max_failures, so a failed try goes straight back to FAULTED with the next cool-down rather than climbing the backoff ladder again, and a run of good_run_seconds is back to normal. S starts it at once; X leaves it stopped; faulted_retry_minutes = [] waits for a person, as before. logs/faulted-<slug>.txt says why, with the last 200 console lines.
  • Restart budget. More than restarts_per_hour (6) automatic restarts in a rolling hour (wall time, so it holds across Huragok's own restarts) also mean FAULTED, decided when the stop completes, so the server is left down. Automatic means watchdog, keepalive, daily, server-program and Workshop-update restarts. A manual restart now does not count, nor does a crash restart; a restart planned after the game or when empty counts even when a person asked for it. A command backend with only a restart command checks the budget before the restart and, over it, leaves the server running ("Not restarting it: it keeps running as it is").
  • Warn before planned stops. Chat warnings at 300, 180, 60 and 30 s before the moment (warn_seconds), as absolute deadlines. No countdown when RCON shows nobody on. A countdown ends early once nobody has been on for empty_seconds (10 s). If the player count is unknown (RCON down), the full countdown runs.
  • After the game. A restart planned after_game waits for finished of the game that was playing (the server can announce finished for the next game early; that is ignored), or for the game to go straight back to a lobby (no_game after playing, as a Halo 3: ODST server's does, 0.9.19), or for the last player to leave, then gives after_game_seconds (15 s) of notice. Planned while the game is already finished, it runs at once. If the game has not ended within 30 minutes (on the monotonic clock), it restarts with the full ladder. A plan runs at once when RCON shows nobody on.
  • When empty. A when_empty plan runs when the last player leaves, or after 30 minutes with the full warning ladder.
  • Plans end with their run (D23). A plan is dropped when its run ends some other way (a daily restart, a crash, a failed start, FAULTED then S): "the restart planned after game (…) is dropped: the server is starting again"; a person's stop drops it too. Its job still runs at the next start, and the new run's first lobby doesn't count as the old game's end.
  • Restart now wins. A restart now replaces any restart planned for later ("the restart planned after game is now a restart now").
  • Restart all (start.cmd restart with no server) restarts only the servers that are up; the others answer "not running, so not restarted". A named stopped server is still started by restart.
  • Daily restart. HH:MM local time, once per date, only in the 30 minutes after the slot (so Huragok opened at noon does not restart everything), and only after min_uptime_seconds (900 s) of uptime. It uses the full warning ladder. A slot inside the hour the clocks skip still fires.
  • Not ours. A server whose RCON port something already listens on (the process backend reads the system's socket table) and that was not started from here is external: watched and moderated, never stopped or restarted. Until it is known whether the port is taken, a stopped server isn't started.
  • Servers found later. A server folder that appears while Huragok runs is read at the next discovery (10 s) and adopted if its process runs; the first server found while Huragok runs with none is booted (started if autostart). running-servers.json keeps the entries of servers left out of this run (servers = [...], a broken folder) until their process dies.
  • Names before numbers. A server is named by its exact name (any case), then its folder slug, then #N or a bare number as its position (Fleet.find, and the same with Huragok not running); a server really called "2" wins over position 2.

A server Huragok makes shares the root's game/ and bans.json (game = "../../game").   • Quick repairs, on the loop (file checks and a tomledit write): a ban list made empty where the file says, or the server pointed at the root's shared one when even its folder isn't here; a content folder made; a game folder without Halo 3 pointed at one here that has it; a [workshop] steamcmd that isn't on this PC replaced by the root's. Each is logged with what the host may want to do (copy the old bans.json over, say) and emitted as server.repaired.
  • Game files (GameFiles): when Halo 3's files (or, for a server that plays them, the campaign missions or ODST's) are still missing, the server waits (waiting_for, the row says WAITING, no failed start counted, looked at again every 30 s) while they're got in a worker thread into the root's game/: copied from MCC (dedicated init --from into a scratch folder, then hard-linked beside what's there) or, with [setup] download_game_files, downloaded with SteamCMD's download_depot on the saved sign-in (+@NoPromptForPassword: never a prompt).   • A port held by the copy it was made from: a stopped server whose port answers but whose own status.json hasn't been written in two minutes isn't taken for external (watched and moderated as if it were this server): it waits, waiting_kind = "port", until the port is free.
  • Workshop updates check steamsetup.cannot_fetch before planning their restart: a SteamCMD that isn't on this PC, or an account with no saved sign-in here, means no restart and a flag (press I) instead of up to three restarts that each put the old copy back.

Watchdog and keepalive

Two independent mechanisms restart a broken server: the keepalive (core) handles a server that stopped answering at all, and the watchdog (a part) handles one that still answers but is dead, stuck or unjoinable. Both ask the Fleet for a restart; neither touches a process directly. Both are the Superintendent's: their lines carry SUPT.

Watchdog cases (0.2.2)

Each case has its own setting in [watchdog]: actnow restarts right away, act restarts after the game: at once when nobody is on or the game has just finished; with players in a lobby, after the next game ends or 30 minutes, watch only logs it and shows it on the dashboard. mode = "watch" turns every case into watch, as a dry run.

How it decides

It evaluates every server every 60 s, and at once when a roster-loss line arrives.

  1. Compute the cases that apply now. Only cases that were not there at the last look act; a server that is very_slow all game still restarts when it then dies.
  2. Take the strongest setting among the new cases (watch < act < actnow). watch, or mode = "watch", logs what it would have done and stops.
  3. Skip if the server is mid-flight: launching, preparing, booting, counting down, stopping or restarting (manager.BUSY).
  4. Skip if a restart is already planned, unless this is actnow and the plan was for later: then the plan becomes a restart now.
  5. actnow: restart now. Players get 30 s of warning, or none when the server dropped everyone or they are stuck on the scoreboard. act: restart after the game. An actnow restart logs [server] METROPOLITAN EMERGENCY! Restarting it now: <reason>.
  6. The restart is recorded "by Watchdog" with a reason players read ("the server dropped its players", "nobody can join", "the game is stuck"…), and counts toward the 6-per-hour budget.
  7. When a new run begins (server.restarted from the manager after a restart it made, or, with the process backend, the console's server.started line, which also marks the built-in layer starting the game again), all history for that server is cleared: drops, frame samples, connections, joins, admissions, memory and the cases found. A first start or a start after backoff emits server.ready, which clears nothing.

Why these defaults

The defaults come from replaying the live server's log through the real watchdog code.

  • Dead: on the live server, the roster loss came about 38 s after a game ended, and nobody could join afterwards. The server program's own rule waits five minutes. Across both live logs (exported 16 and 18 Oct, 46 starts), the dead rule fired on exactly the 13 post-game deaths and on nothing else. Four mass drops that left players on (70 of 73 and 77 of 81 mid-game, 31 of 32 and 122 of 123 after a game) kept letting players in, hence drop_left = 0.
  • No joins: in the first export's log lines (7,652 connections), "connected but never joined" happened only while the server was dead, including one six-hour dead stretch on a version that never printed "Host roster lost". That count, and the replay, used the log's lines only: on a live server the console's join events came too and counted as joins at once, so no_joins could never have fired while Huragok's console was connected. A console join now counts only once that player is still on 120 s after connecting (none of 300 connections on the logs' dead stretches lasted 80 s). The audit's replay with the console's events, across the second export (about 12,000 connections, the first one included), restarted every real dead stretch and fired nothing new on the healthy ones; replay_watchdog.py itself still feeds log events only.
  • Stuck: over 51 healthy game ends in the first export, the next game's countdown finished within 107 s (117 s over 83 normal ends in the second, two long outliers aside; measure_cases.py). 3 minutes gives margin; the earlier 10 minutes was too long. stuck_minutes needs headroom over the playlist's vote time plus load_timeout: lengthen it on a server with long votes or slow loads.
  • Slow frames only watch: with 100+ players on a 2 GB map, the frame rules would have restarted the server mid-game 372 times and faulted it in 22 different hours. A full server is slow anyway, and a restart does not make it faster.

Keepalive

The keepalive checks every 10 s. A server is hung when both status.json has not been rewritten (normally every 5 s) and RCON has not answered, each for hang_seconds (180 s). It only looks at servers that are up and not mid-restart, and it judges each run from when it came up: the files and replies of the run before don't count against it. RCON that never answered in this run counts as quiet. A run with no status.json yet (a new server's first run, frozen before it wrote one) would never count as hung, so once its console has answered during this run, the run's age stands in for the file's; a console that never answered gives no signal at all, and that alone never restarts a server.

  • With act = true it restarts the server at once (no countdown), reason "not responding". It asks once per run, and again after 10 minutes (Keepalive.RETRY) if that same run is still hung; the hourly budget (restarts_per_hour) stops a loop. A server it can't restart (started some other way) is logged: "can't restart it: …".
  • It logs "[X] not responding: status.json last written N s ago, RCON quiet" and "[X] responding again", which the window shows, and emits server.hung and server.recovered (the event log records them). "RCON answered" means a reply to the state refresh, every 30 s.
  • Two signals keep false alarms rare. A frozen game stops both: with a test server's engine worker (probe-engine-worker) suspended on 18 Oct, status.json stopped at once, RCON gave no reply and dropped 51 s in, the program's own supervisor did nothing, and the keepalive restarted it 3 min 4 s after the freeze; it answered RCON 8 s later.
  • Why it matters: on 17 Oct the live server stopped twice in a row, writing nothing at all: 76 minutes with a player on, then 2 s into the next start, for 10 minutes. Reproduced on 18 Oct: text selected in the server program's own console window (it starts with QuickEdit on) holds every log line and, after about 75 KB of output, blocks whatever logs, RCON included. Servers Huragok starts have no console window, so this can't happen to them; one started some other way can only be reported.

What the watchdog depends on

  • Exact log wording. dead, no_joins and the frame cases match server.log lines from v0.9.18 to v0.9.20 by regular expression, anchored at the start of the message. If a release rewords them, those cases go quiet without an error, and nothing warns (The road to 1.0, gap d).
  • The live player list. stuck needs players to be known, and no_joins checks for room and whether a console-admitted player is still on. Players already on when Huragok connects are listed by the refresh it makes on connecting.
  • The console. stuck is judged only while the console is connected (its phase and players are frozen while it's away). An after-game restart waits for a game end it can't see, then restarts after 30 minutes with the full warning ladder, the player count being unknown. no_joins and dead come from server.log and work without it: with the console away, room is assumed and only the log's joins count.
  • A backend that can restart. With attach, every case can only log.

Moderation

Moderation is Vergil's part (VRGL). It has three ways in: in-game ! commands, automod, and the console (the window's A key, the relay, start.cmd rcon). The first two go through one ledger that records who acted and why; console commands are logged but not recorded in that ledger. Bans themselves live in the server's own bans.json; Huragok never keeps a copy. Automod's mutes are the other way round: the server forgets its mutes when it restarts, so automod keeps its own (in automod_strikes) and mutes the player again as they join.

The player is found as for !ban (on the server, or by ID or a name Vergil has seen, never a name's start). tomledit.add_to_list puts them in commands.toml on a line of their own ("<id>", # Bravo: promoted by Alice on 2026-10-19), before the list's closing bracket, adding a comma to the last entry if it lacks one; a one-line list becomes one entry per line; remove_from_list takes that line out. Both go through the safety net (only that list may change, or nothing is written), keep every other line and comment as the host wrote it, and refuse an entry sharing a line with another. The change is in force at once (PartContext.reload_permissions, which runs the same reload as the 2-second look, so the vote-kick immune list follows), logged, and a player who is on is told. Owners change only in the file.

Roles follow the 64-character player ID, never names: anyone can use any name, and one night on the live server had 30 players called "Player". Each command sits in the list of the lowest role allowed to use it, higher roles inherit it, and [off] switches a command off. Rank: nobody can !warn, !mute, !kick, !ban or !strike a player of their own role or above, except owners, and the rule follows the player ID too, so an admin can't !ban an owner's ID while they're away ("Bob is an owner; you can't do that to them."; !strike: "… you can't strike them."). !unmute, !pardon, !unban, !pardonplayer, !strikes, !team, !startvote, !admin, !unbanname and !whois don't check it. commands.toml is looked at every 2 s; a bad edit is logged and the previous version stays in force, a file that is briefly missing or empty (an editor saving it) keeps the roles in force until it has something in it, and a good one emits supervisor.commands_reloaded.

Votes to kick

The server never lets a vote kick its own admins, and keeps a second list of players no vote can kick: its console's immune (immune list, immune add <player | ID>, immune remove <player | ID | name>; in the 0.9.18 and 0.9.20 programs, not 0.9.15; not in RCON.md or help's list). The list lives in the ban list under vote_kick_immune, so every server sharing bans.json reads the same one, and changes apply at once without a restart. immune list's data is {"added": [{"id", "added_by", "added_at"}], "configured": [...]}: configured are dedicated.toml's vote_kick_immune IDs, which the console can't remove. No event goes out when the list changes, and the player isn't told.

parts/commands/votekicks.py (in the always-on commands part, Vergil's) keeps the list in step with commands.toml:

  • When: on rcon.connected for that server, on supervisor.commands_reloaded and every 5 minutes for every connected server, one server at a time (servers usually share the list, so the first one does the work). Each console command waits 3 s at most and a pass stops after 6 s, inside the part's handler limit (15 s by default); what's left waits for the next pass. Console errors never count as part failures.
  • What: every member, moderator and owner (Permissions.listed()) not already on the list, by ID with by: "Vergil" (stored added_by: "Vergil (RCON)"). Admins are left alone: the server protects them. Entries whose added_by is Vergil (RCON) and whose ID commands.toml no longer lists are removed; every other entry (the host's immune add, configured) is never touched. A remove answered "never made" (another server sharing the list removed it first) is fine.
  • Dry run: says once what it would add and remove, and changes nothing; a vote the fallback would cancel is only logged.
  • Refused calls: the server answers a vote to kick an immune player as it's called (<caller> could not call a vote: <name> can't be vote-kicked on this server. in server.log, log.vote_refused). Vergil logs who tried and, when the name is one connected player with a role, tells the caller (one name match) why: BE A HERO! REPORT VIOLATORS! <name> is a member here, so no vote can kick them. If they're breaking the rules, tell the host., at most once per caller per 30 s.
  • Fallback: on a server program without immune (it answers Unknown command; logged once per server), or before the list is in step, an rcon.vote with state called and subject kick <name> whose name means only players with a role (members, moderators, admins and owners: the exact name, else the name without a same-name suffix like (A7B)) is cancelled with cancelvote (by Vergil); everyone reads the server's own cancel line, then BE A HERO! REPORT VIOLATORS! <name> is a member here: no vote can kick them. A name that could also mean an unlisted player is left alone. The list is then synced again.

In-game commands

Players type !command in chat. The line is ordinary public chat, so everyone in the channel sees it; the reply comes back privately with tell, wrapped at 120 characters a line (console output cut at 8 lines, "…and N more lines"). Each player waits 3 s between uses of a command (admins and owners do not); a use inside the cooldown is ignored. !yes and !no are reserved for the server's own votes. A reply that can't be delivered (a slow or restarting server) is dropped, not raised: five slow !players no longer switch every ! command off.

Who a command is for (CommandCall.find_target; !warn, !mute, !kick, !ban, !strike, !strikes, !pardonplayer, !unmute, !admin add), in this order:

  1. #N or the number alone: the player on with that number ("Nobody is #N on this server now. !players lists them.").
  2. A full 64-character player ID.
  3. An exact name on the server, in any case (several: "'x' could be #1 A, #2 B. Use the #number.").
  4. A name Vergil has seen them use (any case: Élodie and ÉLODIE, Straße): the player if they're on; otherwise "Bob isn't on this server now." (several: "… Use the player ID."). !ban bans that player's ID while they're away, and !unmute reaches a player who left, by a seen name or ID.
  5. The first 8 or more characters of a player ID.

The start of a name alone acts on nobody: "Nobody here is called 'bobb'. Did you mean Bobby (#6)? Use #6." (!unmute takes a name's start for a player who is on.) !admin add doesn't look at seen names. !team, !startvote kick and !whois use find_player, which takes a name's start: they punish nobody.

Automod

Automod acts on words on one list, automod.txt, one rule per line: words | kicks | mutes | ban | name; and on names, against that list and names.txt.

  • What it reads: every chat line (not the server's own channel; a muted player's lines never arrive) and every name: as a player joins, and every 5 s for everyone on (each player and name checked once until a list changes, or the console reconnects). Admins and owners are exempt by default. A moderator's own command line (!strike bravo slurs he said <word>) isn't checked when the caller may use that command; a player's (!help <word>) is.
  • What it catches: each listed word in capitals or accents, with digits and symbols for letters (b4dw0rd), with up to 4 other characters between letters, with repeated letters, with Cyrillic or Greek lookalikes, with invisible characters, and as a plural. word* also catches the start of longer words, *word* anywhere, and -word marks an exception. A listed number (1488) matches as written, but for a word with more letters than digits a match with more digits than letters isn't a hit, so "respawn in 45s", "455 kills" and "Team 455" don't hit a three-letter insult (the decision: "a55"-style disguises aren't caught either).
  • Across lines: a word split over lines sent within 10 s is caught; lines within 10 s of a strike count as one strike.
  • Escalation: each strike counts that player's earlier, unpardoned strikes on the same rule (optionally only within forget_after_days) and takes the next step of the line's ladder: the kicks, then the mutes, then the ban. mutes is the number of strikes before the mutes start, then each mute's time (the last repeats; perm is for good); ban is the number of strikes before the permanent ban. Kick times: one per kick, the last repeating until the mutes; none is the server's own kick (out 10, 30, 60, then 120 minutes). A timed kick is a timed ban underneath, because the server's kick times are fixed. Kick times past the start of the mutes overlap them (0.4.4): that strike is a Step("mute", time, kick), the timed ban for the kick's time with the strike's message, and a row with action = 'mute', kick set (the automod database's 3rd step adds the column) and expires = the strike + the kick + the mute, so the mute is Vergil's to put on as they join again once the kick is over; !pardonplayer lifts that ban while the kick lasts, and the mute. Counts have no upper limit (0.4.3's was 20): a line is refused only when a kick or mute time would never be reached before the ban. ladder() works from the strikes where the step can change (Rule.changes()), so a ban after a billion strikes is one line, and strikes in a row that do the same are one entry ("3rd to 9th: muted for 1 day"). A plain kick or a mute goes to every server the player is on (a plain kick of a player on none: nobody is kicked, the strike counts, the reply says so, the row is ok = 0; a mute waits for them to join); a timed kick or ban to the first server they're on, else the strike's. A four-part line, words | timers | chances | name (the 0.2 layout), is read as before, with chances as the ban.
  • Unnamed lines: strikes are kept under the line's name; an unnamed line is rule1, rule2… by position, so its strikes would move to another line if a line were added above it. check, automod's start and each reload warn about an unnamed line whose strikes change what happens (mutes, a ban, or more than one kick time): "… line N has no name, so its strikes are kept under ruleK, and they move to another line if a line is added above it: name it (the 5th part …)".
  • Mutes: the server's mute lasts until its time, an unmute, or the server restarting, and only on that server. So automod's own rows are the list: on every join, on any server, an active automod mute (not pardoned, not lifted, not expired) is sent again for the time left ("KEEP IT CLEAN! You're still muted (…): … left."). The 5 s name check does the same for a player already on whom the server lists as unmuted (a restart Huragok didn't see, or players who rejoined while its console was away: a reconnect re-checks everyone); and when a moderator's shorter mute runs out (rcon.unmute by "time") while Vergil's still has a minute or more, it is sent again. A strike on a player who is on no server mutes them as they join; the time counts from the strike. An unmute from anyone else (an rcon.unmute with a by, or a moderation unmute from a part) marks the rows lifted, so automod doesn't put it back; the strike still counts.
  • Names: a name is never struck. A name with a word of automod.txt in it (with check_names) or an entry of names.txt in it is kicked as it joins, every time, and then pardoned at once (pardon <player ID>), so the server's kick block does not keep the player out once they pick another name. names.txt entries are matched like words (disguises, whole words, * to widen). !strike <player> name appends the player's name, with a # banned <date> by <moderator>: <note> line above it, and kicks them; !unbanname removes it and that line.
  • What the player reads: the rule's name and the strike number ("slurs, strike 2 of 3"), never the word itself. [automod] messages overrides the texts; check and automod's start refuse a message that can't be filled in (a stray brace: write {{ or }}), and at run time a message that still can't be falls back to the default.
  • Manual strikes: !strike <player> <rule> lets a moderator strike for something said in voice; !strike <player> name bans their name; !strikes shows strikes and a mute's time left; !unbanname (admins) takes a name off names.txt.
  • !pardonplayer marks the player's strikes pardoned and lifts what automod did: an unmute when no active mute is left, a kick pardon after a recent plain kick, and only the bans Vergil gave. It reads the server's ban list and lifts a ban only when its banned_by is the strike's (or "<by> (RCON)") within 120 s of the strike, ones whose reply timed out included. With someone else's ban on that ID it sends nothing and says whose ban stays ("<who>'s ban stays (<reason>): it isn't automod's; !unban lifts it"); if the ban list can't be read, nothing is lifted.
  • Dry run: automod ships on, in dry run: it records what it would have done and sends no moderation command and no notice. Dry-run strikes and mutes are counted separately from real ones, so turning dry run off starts every player at zero. !strike <player> name still writes names.txt in dry run; the kicks are dry.
  • Limits today: voice chat is covered only by manual !strike. Strikes and automod's mutes are per machine (one database), not shared between machines. Mutes from !mute or the console are the server's alone and still end when it restarts. The server announces each name kick in chat, with the name.

Reading the lists

automod.txt and names.txt are read every 5 s. They may be UTF-8 (with or without a byte-order mark) or Notepad's "Unicode" (UTF-16 with a byte-order mark); anything else is refused with what to do ("automod.txt isn't saved as UTF-8 (byte N is 0xNN; ANSI, perhaps): save it as UTF-8 in your editor"). A file held by an editor while running keeps the old rules and is read again when the save finishes (at start it keeps automod off, with the reason). A word in automod.txt that is nothing once normalised (a zero-width space, a combining mark, a Hangul filler) is refused naming the line, since it would match every chat line; such an entry in names.txt is skipped.

How the matcher works

  1. Normalise the text (and each listed word the same way): cut to 600 characters; remove Hangul fillers and blank Braille; decompose (Unicode NFKD) and drop every format, combining, enclosing and unassigned character (categories Cf, Mn, Me, Cn: zero-width spaces, accents, tag characters); fold case; map lookalikes to Latin (Cyrillic and Greek letters, ı, ł, ø, ß to ss, æ to ae, œ to oe); shorten any run of 3 or more of one character to 2.
  2. Build one pattern per listed word, letter by letter. Each letter accepts its stand-ins and repeats (a as a 4 @; b 8; e 3 €; g 9 6; i 1 ! |; l 1 |; o 0 (); s 5 $; t 7 +; z 2), and up to 4 characters of anything that isn't a letter or digit (underscores included) may sit between two letters, except those two letters' own stand-ins.
  3. Word edges: without a *, the pattern must not touch another letter or digit on either side, and may end in a plural (s, z or their stand-ins, after an optional e, with up to 3 separators). A leading or trailing * lifts that edge (a trailing one drops the plural too).
  4. The numbers rule: for a word with more letters than digits, a match with more digits than letters is skipped.
  5. One compiled pattern per rule (its words joined), plus one for its - exceptions. A match that lies entirely inside an exception match does not count, and the next match is tried.
  6. Each rule matches at most once per line. When several rules match, the strike goes to the rule whose next step is the most severe (a ban beats a mute, a mute beats a kick; longer beats shorter; on a tie, the earlier line).
  7. Split words: when a line matches nothing, it is joined to the player's earlier lines from the last 10 s (at most 3 kept) and matched again, counting only matches that reach into the new line.

The ledger

Every warn, mute, unmute, kick, ban, unban and pardon from a ! command or automod goes through Moderation.act (moderation.py):

  1. It sends the RCON command with by, so players read "kicked by Alice" or "removed by Vergil" (a warning is a tell, "Warning from Alice: …").
  2. It records the action in SQLite (actions: time, server, kind, target ID and name, by, source, reason, duration, evidence, dry run, ok, the server's reply).
  3. It emits moderation.action for the other parts.
  4. It never resends a command after an error, because it may already have run.

Alongside it, every join is recorded in players, player_names and player_ips: first and last seen, visits, every name and every IP used. !whois reads them (names and actions, not IPs).

Gap: commands typed in the window's console, through the relay or with start.cmd rcon go straight to RCON, as do the ! commands that are not moderation actions (!say, !map, !admin, !team, !startvote and others) and Vergil's own immune-list changes and vote cancels. They are logged in huragok.log and the server records by, but they are not in the actions table, and the relay checks only the command's role, not the target's. In-game admin actions with the game's own / commands are visible only as rcon.kick / rcon.ban events, which are stored only when [eventlog] is on.

The relay for remote moderators

The relay (relay.py, off by default) lets moderators elsewhere use the official RCON client through Huragok, each with their own password, name and role. It is Vergil's.

  • Ports: game port + 1000 speaks the server's WebSocket console protocol (49176 becomes 50176); game port + 2000 speaks Source RCON for third-party panels (no events).
  • Who: [[relay.user]] blocks in settings.toml with name, password (8 to 128 characters, unique) and role (moderator, admin or owner). The password identifies the user.
  • What passes: the command word is the line up to its first plain space. Read-only commands (status, players, bans…) and queries typed alone (password, admin, nextmap…; with the args form, alone means no args) need moderator. A fixed table comes next (tell: moderator; banip, vpnallow, vpnrevoke: admin; password, reload, admin with arguments: owner), then the role commands.toml gives a command that is also an in-game ! command (at least moderator); anything unknown needs owner. [off] applies through the relay, owners included. A line with a control character or a new line, an args-form command with a space in it, and a blank word in the args are refused.
  • How: commands are forwarded on Huragok's own RCON connection with by set to the user's name (15 s for each), so the server's 4 console spots stay free. Events are fanned out to every connected user. Users below admin get replies and events without addresses or device fingerprints: ip, address, device and fingerprint keys at any depth, devices' ids, and IPv4 and IPv6 addresses in text, replaced by "(hidden)", on both protocols. (The decisions: status hides the server's own address from moderators too, and an IP typed in chat is hidden from them.)
  • Lockout: 5 wrong passwords in 10 minutes lock that address out of the relay only, never out of the server.
  • Security: not encrypted, and passwords sit in plain text in settings.toml. Keep address = "127.0.0.1" and reach it through an SSH tunnel or a VPN. Console lines that set a password are masked in the relay's log lines.

How Huragok holds its RCON spot

A server allows 4 signed-in console tools plus one spot kept for its own machine. Huragok signs in on that kept spot using the key the server writes to data/<slug>/rcon-host.key at each start, so moderators keep all 4. A stale key still signs in, silently on a normal spot, so after signing in it re-reads the key and reconnects once if it changed; signed in before the key existed, it moves to the kept spot once the key appears (looked for every 2 s for 2 minutes). Five refused passwords in 10 minutes would lock every tool on the machine out of that server, so a refused password is remembered: it is tried again at once when the server's instance.json gives a different one (looked at every 5 s), once after the server starts again (while fewer than 2 refusals fall in 10 minutes, so Huragok can never lock the machine out itself), else every 10 minutes. The server's lockout line (RCON: <addr> gave a wrong password 5 times; refusing <ip> for 10 minutes., log.rcon_wrong_password) makes it report a lockout ("this machine is locked out of the console for N minutes"), not a wrong password; rcon.auth_failed carries lockout. A good sign-in clears the refusal.

Key flows

Three flows show how the pieces hand work to each other: a server dying after a game (the core uptime case), a restart asked for from outside, and a slur in chat.

A server dies after a game

Solid arrows are requests or events; dashed arrows are what the backend observes. From the log line to a new dedicated takes a few seconds; the rest is the game loading.

  1. Server program: about 38 s after a full game ends, server.log gets "Host roster lost 112 of 112 players in one update (0 now present)".
  2. FileWatcher: reads it within a second and publishes log.roster_lost (lost, of, present, the engine's JSON).
  3. Watchdog: at least 8 lost, at least half of those on, none left: the dead case is new and set to actnow. It emits watchdog.health (critical) and, since nobody is left to warn, asks for a restart with no countdown, reason "the server dropped its players", by Watchdog.
  4. ServerManager: notes an automatic restart against the hourly budget and goes straight to stopping.
  5. ProcessBackend: sends Ctrl+Break through the helper process (SIGINT on Linux).
  6. Server program: dedicated prints "All servers stopped." and exits, usually in under a second; after 30 s it would be killed.
  7. ServerManager: the next tick sees the process gone, and because the stop was a restart, goes to launch.
  8. ProcessBackend: starts dedicated run again, detached, output appended to the console log.
  9. RconClient: wakes on the server.started console line, signs in with the new host key; the manager moves from booting to running.
  10. ServerManager emits server.restarted; the watchdog clears its history for the server.

Without the watchdog, the program's own rule waits five minutes without frames, and on one older version the server sat dead for six hours. If this repeats more than 6 times in an hour, the server ends up FAULTED and stays down.

A restart asked for from outside

  1. start.cmd restart "Slayer" --reason "update" writes records/requests/<id>.json and waits up to 15 s for a reply.
  2. The next Fleet tick reads and deletes the file and calls restart on that manager.
  3. With players on, the manager starts a countdown and replies "restarting (warning players first)"; the reply file is written and the command exits. The countdown carries on without it.
  4. Chat warnings go out at 5, 3 and 1 minutes and 30 s ("PLEASE REMAIN CALM! Server restarting in 5 minutes: update."). If everyone leaves, it stops waiting after 10 s.
  5. At zero: "PARDON OUR DUST! Server is restarting now.", then the same stop, launch, booting and running steps as above.
  6. A manual restart now does not count toward the hourly budget; one planned after the game would.

A slur in chat

  1. The server sends rcon.chat with channel, name, player ID and text.
  2. The bus hands it to the command router (not a ! line, so ignored) and to automod's queue.
  3. Automod skips admins and owners, normalises the text (case, accents, lookalikes, invisible characters, repeats) and matches it against every rule, joining it with the player's lines from the last 10 s to catch split words.
  4. On a match, and outside the 10 s strike cooldown, it counts the player's active strikes on that rule in SQLite and picks the step for this strike, for example the second offence: removed for 1 day.
  5. It tells the player why ("KEEP IT CLEAN! That isn't allowed here (slurs, strike 2 of 3): removed for 1 day. Next time: removed for 7 days."), then calls Moderation.ban with duration 1d and by Vergil. A mute step calls Moderation.mute instead, on every server the player is on, with no separate notice: the server shows the player the reason.
  6. The ledger sends ban <player ID> 1d <message> over RCON, records the action, and emits moderation.action. The server writes bans.json, removes the player, and sends rcon.ban.
  7. Automod records the strike in automod_strikes and emits automod.strike.
  8. In dry run, steps 5 and 6 send nothing and every row is marked as a dry run.

Commands from outside the window

Setting up a new server (N, new)

  1. The folder is built as SERVERS/.new-<slug> (ignored while being made), using the server program's own dedicated init.
  2. Halo 3's files (5.5 GB) and bans.json are shared from the root by default ([setup] share = ["game", "bans"]; content can be added, but each new server gets its own content/): the server's dedicated.toml points at ../../game and ../../bans.json, and game/ is filled once by hard links from a server that has it, or by dedicated init from MCC.
  3. The chosen package adds its playlists, game types, maps and Workshop items.
  4. It picks a free port and makes up an RCON password.
  5. dedicated check runs; if it fails, autostart is turned off.
  6. The folder is renamed into place. The window has Huragok look for it at once and, if the check passed, asks "Start it now?"; new starts it through a running Huragok unless --no-start (with nothing running it says to start Huragok).

Packages live in PACKAGES/<name>/ (package.toml plus playlists/). Seven starters ship: Team Slayer, Big Team Battle, MLG Hardcore, Infection, Scripted Modes, Campaign Co-op, ODST Firefight. A package with a field of the wrong type, or one that sets what's chosen when a server is made (name, port, password…), is listed as broken and can't be used; the others still list. A package with needs_odst = true (or an odst block) gets ODST's files added to the game folder as the server is made (newserver.add_odst_files: dedicated init --maps odst into a scratch folder, then hard links), from the MCC on the PC that has ODST installed. Any server can be saved as a package.

How an update of Huragok runs

  1. The check (3 s after start, then every 6 h) asks GitHub for the latest release of Huragok's repository and compares versions. A newer one is announced in the log with the first lines of its notes. GitHub out of reach is said as such in U: "couldn't ask GitHub whether there's a newer Huragok: …".
  2. Installing needs the copy to run from its own engine/ folder, as the launchers run it.
  3. The release zip (huragok*.zip) is downloaded to records/huragok-<version>.zip and must have the size GitHub lists (else the Content-Length), at most 50 MB ("the download from … stopped after N of M bytes; nothing was changed"); then GitHub's SHA-256 digest when the release gives one. The zip is deleted afterwards either way.
  4. It is unpacked into records/update/; the version inside must match the release.
  5. Everything in engine/ except .venv, plus docs/, the start scripts, README and LICENSE, is renamed into records/previous-<version on disk>/ (an older backup of that name is renamed previous-<V>-<its date>, never deleted), and the new files are renamed in. Renames only: a folder that can't be renamed (a console whose current folder is in engine/, an editor, an antivirus scan) fails the update, and every rename so far is undone. Afterwards engine/huragok must read the new version, or everything is undone. records/last-update.json records the version, what was replaced, the backup's name, what was added and when (updates.last_update).
  6. When requirements.txt changed, the new packages are installed into engine/.venv (10 minutes at most). If that fails, updates.put_back puts the old files back ("…; the old version's files are back in place") and nothing relaunches.
  7. Huragok waits until no server is busy (launching, preparing, booting, counting down, stopping, restarting, in backoff) and none has a plan or a job waiting, checked every 2 s for at most 30 minutes; then it stops without stopping the servers and exits with code 10. A manual update waits the same way. The start loop starts the new version, which adopts the running servers.
  8. If the new version exits within 2 minutes with anything but a deliberate code (0, 3, 4) or 10, a settings problem the new version is stricter about included, the start loop puts the previous version back (updates.put_back from last-update.json), logs it loudly, writes records/failed-update.json (the version, the one restored, the exit code, the time) and starts the old version. That version then says it once in its log and isn't installed again by itself; the note goes when the failed version itself runs.

How a server program update runs

  1. At start (after 20 s) and then every check_hours (1, the least) the check reads the latest release of ProjectReclaimer/project-reclaimer-releases, with its published_at, and compares it with the version each running server reports over RCON and with the --version of each program copy that servers with auto_update off run (asked once per file; the answer read loosely: case, a v prefix, "Project Reclaimer X" or a bare version).
  2. Installing (U, update --program, or [server_updates] install) downloads project-reclaimer-dedicated-v<version>.exe, checks its size (300 MB at most) and, when the release has SHA256SUMS.txt, its checksum; a missing entry in that file, or a wrong one, stops the install with nothing changed.
  3. Each copy is asked its --version (as_new_as); one that is the release or newer (a pre-release, say) is left as it is and logged ("Left … as it is: it is Project Reclaimer 0.9.21, newer than 0.9.20"), so a server is never taken back to a program that may not know its settings. A copy whose answer isn't a version Huragok can compare is never replaced; one that doesn't answer at all is. When every copy is current, the install stops with nothing changed.
  4. The copies to replace are the root's and those of servers with auto_update off. The new file goes to <file>.new beside each (copied for the first place, hard-linked from it for the others, copied where a link is not possible); then each old file moves to records/previous-program/<time>/<folder>/ (with a version.txt) and the .new file is renamed in. A running program can be moved but not overwritten on Windows, so servers keep running on the old file until they restart. If one place fails, every place already done gets its old file back: "couldn't put the new program at …: …; nothing was changed".
  5. Each running server whose program file was replaced gets a restart after_game (or now), reason "updating to <version>", counted as automatic. server.program_updated is emitted.

Servers with auto_update on are left out of this bulk install. For them, Huragok watches, and steps in when the update didn't happen:

  1. Their console lines are events (files.CONSOLE_PATTERNS): Automatic updates enabled: … and Automatic updates requested, but the update feed is disabled … (server.self_update, at the start), Downloading Project Reclaimer <version>... (server.update_downloading), Automatic update failed; retrying in an hour: <reason> and The update check failed: <reason> (server.update_failed). The strings come from the 0.9.20 program file.
  2. A server is overdue when it runs an older version than the newest release and either said its update failed (or its feed is off), or 70 minutes (OVERDUE: its hourly look plus time to install) have passed since the later of the release's published_at and the server's start as seen here (server.started, or its first sign-in). Stopped servers are never overdue: they look as they start. review() runs every 60 s with no network, and right after a failure line.
  3. For an overdue server ([server_updates] fallback, on; the process backend only, as only it runs a program file Huragok can replace; other backends get one log line), take_over downloads and checks the release once into records/program-download/ (older downloads removed), adds a StoppedJob "installing Project Reclaimer <version>", sets the flag Project Reclaimer <version>: installs after this game and plans a restart after_game, reason "updating to Project Reclaimer <version>". Once per server and version. A failed download shows "! Project Reclaimer <v>: the download failed" and is tried again after check_hours.
  4. The job, with the server stopped (swap_program): nothing to do when the server's program file already hashes the same as the download; otherwise the download is written as <file>.new, the old file goes to records/previous-program/<time>/<folder>/ and the new one is renamed in. A root copy that other servers run too is left alone: the server gets its own copy in its folder, which the process backend finds first. After a swap, leftover *.exe.old files in its folder are removed (nothing runs them while it's stopped).
  5. A swap that fails (an antivirus or Controlled Folder Access holding the file, say) is tried again after 1, 4 and 12 hours (SWAP_RETRY_HOURS, each at least check_hours; the flag says "! Project Reclaimer <v> didn't install: tried again in N hour(s) (U to try now)"); after the 4th failure it stops and waits for U: "! Project Reclaimer <v> didn't install (4 tries): U to try again", with the log naming what may hold the file. Each try is one more restart of the server. A release GitHub pulls (its latest goes back to an older one) is dropped: its download, plans, jobs and flags, and it is never installed.
  6. When it signs in on the new version, the flag goes. If it updated itself before its game ended, the job is dropped and Huragok's planned restart (recognised by its reason) cancelled. If it comes back still behind after the file was put in place, it runs some other file: the flag and an error say so, and it isn't tried again that run.
  7. U and update --program also take over every running self-updating server still behind, with the chosen when, and clear its swap failures.
  8. A program older than its dedicated.toml can't start (it parses the file before its updater runs; tested 2026-10-18: 0.9.15 stops at unknown field `auto_reload` in a file 0.9.20 wrote), so it never gets to update itself. The manager's _fail emits server.start_failed with the console lines since that start (manager.since_start). When they hold unknown field|variant `…` and the file's name, _diagnose asks the program --version (once per file, through wine on Linux) and compares it with the newest release. Older, with auto_update and fallback on and the process backend: the release is downloaded and a StoppedJob puts it in place before the next try (the backoff's). The newest already (or newer): the setting is logged once as a mistake in the file and left. Otherwise (auto_update or fallback off, or another backend): one log line saying what to do.
  9. The server program's console line Update installed; restarting all servers. (server.updating) is logged as PARDON OUR DUST! Project Reclaimer installed a new release by itself (auto_update)…. The program renames its file to project-reclaimer.exe.old, writes the new one, stops its servers and starts them from the new file; the outer process stays on the old file until its next full restart.
  10. When a server's console signs in with a newer version than it had (rcon.connected), the log says now on Project Reclaimer <version> (was <version>) and server.program_updated is emitted.
  11. With [server_updates] follow (on), every other self-updating server still on an older version gets a restart after_game, reason "Project Reclaimer <version> is out; it updates as it starts": the program looks for releases as it starts, so the fleet is in step within a game instead of within the hour.
  12. After a self-update (the first console sign-in after server.updating) the outer process still runs from project-reclaimer.exe.old, which the program's next update may be unable to replace while it's in use (untested). With the process backend, Huragok always adds a StoppedJob that removes the .old file, and plans a restart when_empty unless another restart is already planned: right after an update nobody can be on yet (players must update their game first), so it is usually at once.

check (and the dashboard's problems) flags a self-updating server whose program file another server also runs ("two servers must never update one program file", as the hosting guide puts it) or whose folder can't be written to.

How a Workshop update runs

The server program updates the Workshop items it lists only "once no server whose games use the mod has players", which a busy server may never reach; players who already have the new version can't join meanwhile. [workshop_updates] install = "after_game" (the default; when_empty leaves it to the program, off to the host; per server with workshop_updates in its settings.toml [[server]] block) does this instead (workshopupdates.py):

  1. 30 s after start and then every check_minutes (5; 5 to 10080, or 0 for no looks; the program's own minimum is also 5) it posts the listed item IDs to Steam's public ISteamRemoteStorage/GetPublishedFileDetails (no sign-in) and compares time_updated (and hcontent_file, when the receipt's manifest matches nothing is newer) with each server's content/Mods/Workshop/<item>/reclaimer-workshop-version.json (item, manifest, updated). The console line Workshop <id>: update downloaded; it installs once … no players counts too.
  2. A newer version adds a StoppedJob to the server's manager, sets the dashboard flag mod update waiting: <title> (<date>); installs after this game, and plans a restart after_game with the reason "installing a new version of <title>" (once per item and version, never for a version already swapped in or one that has failed 3 times; a host's K cancel stands, and the job waits for the next start).
  3. At the start after the stop the manager is preparing. The job first puts right any job cut short before it, then writes a marker (<slug>-<time>.moving.json) in .huragok-workshop-previous/ next to the content folder, removes a leftover workshop-install.lock (the server is stopped and nothing else uses its content), moves each waiting item's folder aside there (same drive: an instant rename) and runs dedicated mods. Tested on 2026-10-18: dedicated mods over an old copy keeps it ("installed"), while with the folder gone it fetched the newest version of a 2 GB map in 38 s from SteamCMD's cache in data/workshop-cache.
  4. With a receipt newer than the old one the old copy is deleted and server.workshop_updated emitted. Otherwise (the fetch failed, or brought back the same version) the half-fetched folder is removed, the old one goes back, the server starts on it, and the item is tried again after a later game, at most 3 times per version (MAX_TRIES): then "… didn't install after 3 tries …; Huragok stops trying that version until a newer one comes out. To try again: U -> Workshop mods", with the flag "! <title>: the new version didn't install (3 tries): U -> Workshop mods to try again". Each retry is one more after-game restart. A failed SteamCMD sign-in (in the console or the job's output) sets a red ! SteamCMD sign-in failed: press I to sign in again flag.
  5. A job cut short is put right from its marker: Huragok closing mid-fetch stops the fetch and puts the old copies back at once; after a crash, they go back at the next start (or before the next job).
  6. Servers sharing a content folder are left to the program (it swaps a shared item for all of them at once): after_game acts as when_empty for them, and U → Workshop mods refuses them ("its content folder is shared with …, so the server program installs the new version for all of them once nobody's on"). The console saying an item was installed by the server itself (installing the update, updated) clears what was waiting.

The service also writes update_check_minutes into the servers' files (at each start, for servers with items whose value differs), so each server downloads the new version during the game and the swap mostly copies from its cache. U → Workshop mods shows each item's installed and Steam versions and installs waiting ones after the game or now (check_workshop, update_workshop verbs), clearing the item's failure count.

The loop

  1. Draw the dashboard (render), then wait up to 1 s for a key. A frame that can't be drawn is logged ("the dashboard couldn't be drawn", at most once a minute) and replaced by a red line, "The dashboard couldn't be drawn (logs/huragok.log says why). The keys still work: Q closes the window." (_draw_failed).
  2. A key maps to a screen coroutine (S, X, R … Q; ? is H; Ctrl+C is Q). The screen runs on the loop, so a screen must await rather than block. Slow work goes to a worker thread through Menu.slow, which says "This takes a while: keys pressed meanwhile are ignored until it's done." and empties the key queue afterwards, so a stray Esc or Q never answers the next question (a new server, the SteamCMD install, sign-in checks, ODST's files, the catalogue, a server's own content, the clean-up scan). The Workshop screen's console log (its last 256 KB), drive probes and folder walks, the PATH change, W's start at boot, port probes and picking a program copy run in threads too.
  3. While a screen is open, log lines and server events are held by Interruptions and shown together once a second passes without new ones (at most 4 s while they keep coming). The waiting question and whatever was typed are drawn again under them.
  4. A screen that raises is caught: the error is shown for 10 s and the dashboard comes back. A screen can never take Huragok down.
  5. A question left alone for 2 minutes (PROMPT_TIMEOUT) prints "(timed out)" and gives the window back; the A console's prompt too, even while events arrive.

Terminal and keyboard

  • Output goes through tui.ConsoleWriter, a daemon thread started on the first write. A dashboard frame still waiting is replaced by the newer one; screens' text stays in order. When a classic console takes no output (text selected with Edit > Mark, or Pause pressed), at most 1,000,000 characters wait, then the oldest are dropped and the next write says "(N piece(s) of this window's output were dropped while it took none: text was selected in it, or Pause was pressed. logs/window.log has what the screens showed.)". It is flushed at exit. A character the console's code page lacks is written as "?".
  • Keys come from a reader thread (tui.Keyboard), as names (a character, ENTER, ESC, BACKSPACE, TAB, CTRL_C). On Windows they are console key events read with ReadConsoleInputW from CONIN$, so "à" and other characters that share a code with the arrow keys' prefix type correctly; msvcrt is the fallback when the console can't be opened. On Linux, termios cbreak mode with escape sequences skipped.
  • Ctrl+C in the supervising window arrives as SIGINT, which the window turns into the CTRL_C key (a second press within 1 s is the same one): on the dashboard it opens Q's question, in a prompt it cancels. Ctrl+Z is ignored on Linux.
  • Text from players and servers (names, chat, replies, console lines) is cleaned before it reaches the terminal or window.log (tui.clean): a tab becomes a space, other control characters and lone surrogates "?", so an escape sequence in a name can't drive the terminal. Plain command-line output is cleaned the same way.
  • Width is measured in display columns (tui.cells, cut, pad): wide characters (CJK, emoji) take 2, combining marks and format characters 0, so a name cut inside an emoji still lines up. Rules and columns never grow wider than 110 columns.
  • The dashboard redraws in place, always in colour: NO_COLOR applies to command-line output only.
  • On Windows, QuickEdit is switched off for the supervising window, so a click doesn't select text and pause the console in the first place.

Setup and management in depth

Management prefers the server's own live reload: Huragok writes the file, the server (v0.9.18, auto_reload on) re-reads it within a couple of seconds, and the result shows as an event. RCON is used where the change is about players. Every write to a TOML file goes through tomledit.py's check (below).

TOML edits: the safety net

tomledit.py edits in place, keeping every comment and the layout: top-level keys, keys in a table and [[server]] blocks. Each change goes through _Edit: the old text is read and parsed with tomllib, the change is made to what it read as, the new text is parsed again and must equal exactly that; then it is written to a temporary file (<name>.<pid>-<n>.tmp) and renamed over the old one (file permissions kept on Linux). Anything else and the file is left byte for byte, with "couldn't change X safely in <file>: <why>; edit it by hand (O opens it)" (why: "other values would change too (…)", "it isn't valid TOML now (…)", "it isn't UTF-8 text").

  • Refused, without showing the value: dotted keys (rcon.password = …), an inline table (rcon = { … }) where a table would be written, a campaign written as a [server.campaign] sub-table or dotted keys.
  • Understood: multi-line arrays and strings (""", '''), quoted and literal keys and headers, commented-out #key = lines and # [table] headers (a commented # [workshop] example becomes the live table). A value over several lines, like the admins list dedicated init writes, is replaced whole.
  • Written safely: control characters, DEL, the C1 range (NEL included) and the line and paragraph separators are written as \uXXXX; files are split on newlines only.

Huragok's own files (D → S, C, A, N)

D's list puts Huragok's four files above the servers, by letter (servers keep their dashboard numbers, so a script that picked a server with its number still does). Each file has its own screens in menu_files.py; nothing there needs the file's format, and every change is checked before it replaces the file:

  • S, settings.toml: hostsettings.py catalogues every setting the template writes (a test holds them in step), each with its section, type (bool, int, float, text, choice, time of day, numbers, names, a command's words, roles, what new servers share, a path), default, bounds and group, and the backend it belongs to ([process], [docker] or [command] shown only with that backend). A change is made with tomledit on a copy beside the file (.settings.toml.<pid>.check); hostsettings.problems reads the copy with config.load and runs each enabled part's preflight and check_config (parts.config_problem, shared with check); a problem the original didn't have refuses the change ("Not changed (<what>): <why>"), otherwise the copy replaces the file. The relay's moderators are [[relay.user]] blocks (tomledit.add_array_block, set_array_block_key, remove_array_block; a new one goes after the last, or after the table's own lines and the comments that follow them). It applies when Huragok starts again.
  • C, commands.toml: permissions.add_player (one role each: out of the others), remove_player, set_command_role (out of every role's list, into the new one with what it does), set_command_off, set_top; each on a copy read with load_permissions first. Players are picked from storage.recent_players (read-only from the records). A missing file is offered as init writes it.
  • A, automod.txt: rules shown with rules.ladder ("1st: removed for 1 hour; 2nd and after: muted for 1 day"); rules.rule_line writes a rule in five parts when it has a name (four parts ending in a name read as 0.2's layout) and leaves empty parts off the end otherwise; rules.change_rule adds, replaces or removes one line and parses the whole new list before writing, so a duplicate name or a bad time is refused. Tried lines go through Vergil's own Matcher.
  • N, names.txt: rules.add_name and rules.remove_name, the same functions !strike … name and !unbanname use.

Live settings (D)

livesettings.py holds every setting a host can change about a server: its key, where it lives (the server's block, the file's top, [rcon], [master], [vpn], [workshop], or Huragok's own settings.toml block), its type (bool, int, choice, text, list, Workshop IDs, https addresses, chat lines, folder, time of day, and the special what it plays), the program's default, its group, when the server applies it, and the program version it first appeared in (since). D lists the 11 groups (Joining, What it plays, Gameplay, Voice and chat, Safety and admins, Mods and the Workshop, Updates, Listing and network, Remote console, Folders and files, Huragok's own) with counts and a summary of their values, then a group's settings with value and origin (this server, [defaults], the file, a table, settings.toml, the program's default, or unset). Choices are numbered lists; passwords display as "set (n characters)", since the window's transcript is a file. Huragok's own (autostart, daily restart, Workshop update mode) go through the server_setting verb, which writes settings.toml and updates the live overrides and ServerConfig at once.

A new value is checked before it is written, and refused rather than written when the program would refuse it:

  • Its own rules: ranges, player IDs, folders that exist, 8 to 128-character console passwords, join passwords of 128 bytes at most, 5-minute minimum Workshop checks.
  • Against the rest of the file (check_value): min players above max ("min_players (N) can't be more than max_players (M)"); more than 16 on a campaign or ODST server; a host name over 48 characters or with control characters; a stats server that isn't an http(s) address, "off" or empty; a public address that isn't an IPv4 address or DNS name; a [master] origin that isn't an http(s) address; a console address that isn't an IP address; a port that is the discovery master's or any server's here (disabled and left-out blocks included).
  • Against the server's program version: "camera needs Project Reclaimer 0.9.20 or newer (this server has 0.9.18)". since: camera 0.9.20; odst and the campaign's sprint, sprint_speed_percent, sprint_stamina_seconds and skulls 0.9.19; trust_player_games, customization, require_customization, no_vanilla_characters and auto_reload 0.9.18 (at the latest). The version is the one the server reported running, else its program file's own --version, else unknown (no check).
  • "New value": Enter on an empty line leaves the value as it was; emptying a set value asks first ("Empty X?", No by default); the console password can't be emptied there (Huragok needs the console); a password shows as stars and goes into window.log as ********.

What it plays writes one kind and takes the others out in the same write (livesettings.write_plays over PLAYS_KEYS: map, game, base map, variant, campaign, odst; "Use this playlist" in G and playlist use too): a playlist from playlists/; a map and a game from the catalogue (dedicated content), with a base map for a Forge map on a mod map; a preset from content/Game Modes; campaign = { mission, insertion, difficulty, custom_characters, modifiers } with the nine missions by name and the insertion point bounded by the mission (MISSION_STARTS); or (0.9.19) odst = { mode, mission, insertion, variant, difficulty, modifiers }, a campaign mission or Firefight map and game type picked from dedicated content odst (odst.parse_listing; odst.builtin() is 0.9.20's listing, used when the program can't be asked). Campaign modifiers, and an ODST campaign mission's (not Firefight's), ask about enemy health and damage and (0.9.19) sprint, sprint_speed_percent (110-200) and sprint_stamina_seconds (1-30); skulls (a number the guide doesn't explain) and anything else already there is kept. A campaign or ODST server with max_players over 16 won't start, so D offers to set 16 first. An ODST server's game folder needs ODST's files, which D offers to add.

serverops.py renames a stopped server and gives a server sharing a content folder its own. Stopped means idle, faulted or offline; otherwise "<why>: stop it first (X)", such as "the Superintendent is about to restart it (backoff): stop it first (X)". Making a new server (N, new), step by step

  1. Check the name: 1 to 48 characters, no leading . or _, none of <>:"/\|?*, no control or invisible characters, no trailing space or dot, not a Windows device name (CON, NUL, COM1…), and not a name or slug another server uses (disabled and broken servers' names count). Pick the port: one above the highest port any server uses, from 49176, checked to be free; a port typed is 1024 to 65535 and players 1 to 127 (16 for co-op and ODST), and N asks again for one outside them. Make a 32-character RCON password with secrets.
  2. Build in SERVERS/.new-<slug>/, which discovery ignores, so a half-made server is never started.
  3. Shared folders ([setup] share, game and bans by default) at the root, referenced as relative paths (../../game). The root's game/ is filled once, by hard links from a folder that has it (no space on the same drive) or by dedicated init from MCC; a server that doesn't share it gets its own the same way, and with no MCC folder given it links the root's game folder (never MCC's own).
  4. Give it the server program when it needs one of its own (it updates itself, or the root has no copy): hard-linked, or copied across drives. Otherwise the root's copy runs it.
  5. Copy host_name, stats_server, public_address and upnp from an existing server, so the new one matches.
  6. Apply the package: playlists, content, its [server] keys, Workshop items. A content file already there is never replaced (the notes name it).
  7. Run dedicated check. After a failed check, autostart = false is written before the folder appears.
  8. Rename into place, whatever the check found. A build that fails leaves nothing behind ("couldn't make X: …; nothing was left half-made"; the shared root folders it made stay). Otherwise it reports Made <folder>. Feet first into hell.

Workshop items and SteamCMD (I, G)

  • Finding SteamCMD: [setup] steamcmd, steamcmd/ under the root, C:\steamcmd on Windows (~/steamcmd/steamcmd.sh and /usr/games/steamcmd on Linux), then PATH; or I installs it.
  • Signing in: the account must own MCC (anonymous sign-in cannot fetch MCC items). Account names are 2 to 64 letters, digits and underscores (checked at I and steam login). It signs in once in its own window, whose command line is checked and quoted; Steam caches the login. No password is ever written to a file. Esc at the sign-in writes nothing.
  • Configuring: I writes [workshop] (SteamCMD path and username) into every server's dedicated.toml and [setup] steamcmd and steam_username into settings.toml, and can add SteamCMD to PATH.
  • Adding items to a running server: the item list is written to dedicated.toml; the server fetches on reload. Huragok follows the server's console for Workshop <id>: … and Skipped map package … lines (the last 256 KB of the console log, read in a thread) instead of running a second SteamCMD, which used to hang the window.
  • Adding items to a stopped server: dedicated mods runs SteamCMD, with output streamed and Esc to cancel (Ctrl+Break first, then the whole process tree, SteamCMD included).
  • Forge layouts that mods ship can be installed into content/Maps; a mod's title is made a safe file name (a mod titled ".." can't write outside Maps/).

The server program's own commands

dedicated.py runs project-reclaimer.exe dedicated <command> (through wine on Linux), each a short process beside the running server. A command for a server folder runs that folder's own program copy, else the root's; root-level commands (init, mode-check, the copy new links) use [setup] program, or else the newest copy among the root's and the servers' by --version, asked once per file (a release-named file is ranked by the version in its name: 0.9.10 above 0.9.9) (D21). init, check, mods and anything the window streams get 900 s; the rest 120 s. A timeout, or Esc on a streamed one, ends the whole process tree (Ctrl+Break first on Esc), and nothing waits on its output after. Commands used: init, check, content, playlist new, playlist show, mods, bans, reload, mode-check and --version.

Game content

Huragok manages what a server plays through the server program's own tools, never by guessing names: it lists what is there, lets the host pick by number, and has the program check the result.

What it handles

  • Catalogue (catalogue.py): Halo 3's maps, map variants, game types, game variants, mod maps (hand-installed and Workshop) and the Forge layouts mods ship, built from dedicated content, mods' ModInfo.json and the Workshop list. Every picker numbers these. A mod whose ModInfo.json can't be read is skipped, not the whole catalogue.
  • Playlists (playlists.py): playlists/<name>.playlist.json, version 2, 3 to 128 games, each a map plus a game type with weight, rules and options. The builder picks map and game-type pairs. Every save is checked first as a draft (playlists/.<name>.huragok-draft.json, run through dedicated playlist show, then deleted), and games the program cannot play can be dropped. A playlist a server plays is never replaced by one the program refuses ("Leave it unsaved"); any other can be kept as it is to fix by hand.
  • MCC variants (contentimport.py): MCC ships Halo 3's matchmaking variants (320 map variants, 334 game variants: MLG, Team Hardcore, Infection, Grifball…). Import copies them into a From MCC/ folder in the server's content/Maps and content/Game Modes, skipping a file already there (content --import --overwrite replaces it); the server picks them up while running. MCC is found (contentimport.find_mcc) from the folder given (quotes, as Explorer's "Copy as path" writes them, are taken off), then only where Steam's own records say it is: Steam's folder (the registry's SteamPath and InstallPath; Program Files only when neither is set; Steam's own links on Linux), the libraries its libraryfolders.vdf lists (in steamapps/ and the older config/) with the games each holds, and the folder MCC's appmanifest_976730.acf names. Since 0.4.1 no drive is searched and no folder guessed: looking through a host's PC is a privacy problem (the host's call). In a worker thread.
  • Content writes break hard links: imports, Forge layouts, playlists, presets and vote images are written to a temporary file and renamed over the old one (contentimport.copy_replacing, Playlist.save, Preset.save), so a server's own copy never changes a file it shares with another through a hard link.
  • Workshop items: SteamCMD with an account that owns MCC (anonymous sign-in cannot fetch MCC items). A running server fetches its items itself on reload; Huragok follows its console instead of running a second SteamCMD, which used to hang the window. A map without .mapinfo is skipped by the server, and Huragok says so.
  • Next game: the dashboard's game column shows status's next (a nextmap override) or an open playlist vote. It comes from the 30-second refresh.

Direction already decided

Sharing one content/ folder across servers is a flawed direction: servers disagree about where things are, and Workshop items ended up per server anyway. New servers get their own content/ by default ([setup] share = ["game", "bans"]), and a server that shares one can get its own with D (serverops.own_content). What stays shared is one ban list, and a mute list is to be shared the same way. Custom games (presets) are built: G → Custom games.

Diagnostics

  • start.cmd check: settings (including "Settings that do nothing" and "Values from an older version"), server folders, commands.toml, each enabled part's own checks (preflight: automod's exempt_roles, messages, unnamed ladder lines…), playlists' game option labels against each server's own program version, backend problems, whether Huragok is running. Nothing is started. Warnings leave it ready ("Ready, but read the settings warnings above").
  • start.cmd status: each server's state from records/live.json, under the Superintendent's face line. It trusts the lock: it says when the status file is old or "Huragok is starting again", and exits 5 when nothing runs.
  • start.cmd watch <server>: follows a console log, coloured by content; watch huragok (or supervisor, superintendent, vergil, events, log) follows Huragok's log, unless a server has that name.
  • The !health command and the 15-minute health line: level, players, phase, RCON latency, status.json age, slow minutes in the last hour, memory, upload rate.

A third checks that start.sh sets itself up (first start, exit code 3), and a fourth builds the Docker image and runs --version, init and check in it. linux-check/run.ps1 runs the suite plus a two-server deployed root in a Linux container, dashboard included; its inside.sh now fails when the tests fail (it used to pipe pytest through tail, which lost the result) and polls for the servers instead of sleeping.

What the tests miss: anything only the real server program or real players would show (The road to 1.0, section 4), a real Task Scheduler job, a real antivirus holding files. The state-refresh defect of 0.2.0 to 0.2.1 passed the whole suite because its exception died with the loop's task; every test now fails when asyncio logs such an error.

Releasing and deploying

  1. Set __version__ in engine/huragok/__init__.py, add the changes to docs/changelog.md, commit and push. Commits are authored as the user only.
  2. Tag vX.Y.Z, make huragok-X.Y.Z.zip with git archive --prefix=huragok/ (.github/, engine/tests/, .gitattributes and .gitignore are export-ignore), publish with gh release create, titled "Huragok X.Y.Z". The release notes' first lines are what running copies of Huragok show.
  3. Running copies find it within 6 hours and offer it.

Before each release: commit everything (git status shows nothing untracked under engine/) and let CI pass, the release-zip job included (docs/development.md, Releasing).

On the development PC, deploy.ps1 copies the clean build in the repository folder into DEPLOY/ the way a host update does (engine without .venv and tests, docs, start scripts, README, LICENSE), and stops when a copy fails (robocopy's exit code 8 or more). It refuses while Huragok runs from DEPLOY/ (it checks records/huragok.pid, and supervisor.pid as 0.2.1 wrote it). The routine after every change: close the DEPLOY window (servers keep running), run deploy.ps1, start it again.

Security and privacy

The security model is "the machine is trusted, the network is not": everything sensitive sits in the root folder in plain text, and the only network listeners are the server's own console and the optional relay, both meant for localhost.

Trust boundaries

Passwords typed into a screen are written to window.log as ******** (D shows them as stars and as "set (n characters)"). Personal data kept

  • Players: player ID, every name used, every IP used, first and last seen, visit count. Kept indefinitely; there is no deletion tool.
  • Moderation: every action with target, reason and evidence (the offending chat line), and every automod strike.
  • Event log (when on): every event, including join IPs, one file per day.
  • Logs: player names and IDs in huragok.log and the console logs.

No retention policy exists yet. If one is needed, the natural places are a forget_after_days for the player tables (automod already has one for strikes) and a cleanup of logs/events/.

Process privileges

Huragok and its servers run as the logged-in user, with no elevation. Stopping a server on Windows uses a small helper process that attaches to the server's console to send Ctrl+Break; it needs no special rights. The one step that asks for an administrator is C's firewall rules (records/open-firewall.ps1, run elevated after Windows asks).

Compatibility, versions and migration

Huragok is written against Project Reclaimer v0.9.18 (what the live server runs) and RCON protocol 1, and tested on v0.9.15 and v0.9.20 as well. It keeps working across releases as long as the program's interfaces hold; the weakest coupling is the wording of log lines, and nothing warns when it changes.

Platform and runtime

  • Python 3.11 to 3.14 in CI (3.11 is the floor because of tomllib). Dependencies: websockets 13 or newer (its asyncio client and server) and psutil 5.9 or newer.
  • Windows 10 and 11 (the live host is Windows 11): console APIs through ctypes (ReadConsoleInputW, QuickEdit, Ctrl+Break, shared file opens, job objects), msvcrt as the keyboard's fallback.
  • Linux (on hold): the same code, and CI runs the suite on Ubuntu, but nothing is tested end to end; the server program runs through wine. The Docker image (python:3.12-slim, built as huragok, its files in /huragok, running as the user huragok, start --no-menu so a settings problem is retried) can only watch and moderate (attach), because it cannot start the servers' containers. 0.2.1's image used /supervisor: an old compose file mounting that starts with fresh files.

How older installs carry over

  • Host files are never replaced by an update. Up to 0.4.0, new settings weren't added to an existing settings.toml (the code's defaults applied); since 0.4.1 the new version's steps add them, with their comments, and turn retired settings into comments (Hosts' files across updates). An install from 0.2.1 gets the new watchdog cases with their defaults.
  • The reverse also holds: a settings.toml written by 0.2.0 says mode = "watch", and it stays that way until the host changes it.
  • Old names still read: backend = "windows" and a [windows] section mean process; server_folder = ".." keeps the 0.1 layout; 0.2.1's slow_frames sets slow and very_slow when they are not set.
  • From Reclaimer Supervisor 0.2.1: 0.2.1 can't update itself to this version (its updater looks for engine/reclaimer_supervisor in the download, and the decision was no bridge across the rename, since nothing had been deployed): a 0.2.1 host installs this version by hand into the same folder, keeping its own files. Every section and key kept its name, so a 0.2.1 settings.toml loads unchanged. It names database = "records/supervisor.sqlite3", log_file = "logs/supervisor.log", name = "Supervisor" and [automod] name = "AutoMod", so an updated install keeps them; only a newly written settings.toml has huragok.sqlite3, huragok.log, "Superintendent" and "Vergil". The lock is records/huragok.pid whatever the settings say, and a live 0.2.1 records/supervisor.pid counts as running.
  • A start-at-boot item made by 0.2.1 (Reclaimer Supervisor.cmd in the Startup folder, or reclaimer-supervisor.service) still opens the window at login and counts as on: desktop.old_startup_paths() finds it, W turned on replaces it with Huragok.cmd / huragok.service, and W turned off removes both. A 0.2.1 [updates] repository naming LittleGroove/Project-Reclaimer-Server-Supervisor is read as the new address (config.RENAMED_REPOSITORIES), so it never depends on GitHub's forwarding.
  • A deleted settings.toml, commands.toml, automod.txt or names.txt is written again with defaults at the next start.
  • An automod.txt from 0.2.x reads the same: its four-part lines are the 0.2 layout. check names those lines. A name on that list is now kicked until it changes instead of being struck.
  • Mistakes are named, not ignored: an unknown section, a [[server]] key that does not exist, a wrong type (naming settings.toml, not the server's file) or a value under its minimum stops Huragok from starting, with the reason. A key that isn't a setting anywhere else (a misspelling, [relay] enable, a line appended at the end that lands in the last table) is a warning, named at the start, on the dashboard and in check under "Settings that do nothing", with a close spelling or the section it belongs to.
  • Values an older version wrote are named in check ("Values from an older version") and the start log (config.OLD_VALUES): [watchdog] mode = "watch" (0.2.0's default: the watchdog only logs; "act" since 0.2.1), 0.2.1's slow_frames, [setup] share with content, [server_updates] check_hours = 6 (now 1), and the old repository name. Retired keys (config.RETIRED: [process] disable_auto_update) are named under [windows] too when that's where the line is.
  • Settings a server's program is too old for are refused by D, with the version each needs (since: camera 0.9.20; odst and the campaign's sprint and skulls 0.9.19; auto_reload, trust_player_games, customization, require_customization, no_vanilla_characters 0.9.18).
  • The database migrates itself: each owner (core, automod, any part) has a version in schema_versions, and released migration steps are never edited, only added to.

Performance and scale

Huragok is light next to the servers it runs. Measured on the development PC on 2026-10-17 (before the audit added the console's writer thread), with 4 servers configured and 2 running empty: it used 46 MB of memory, 5 threads and 1.4% of one CPU core over 10 s, while each server's process tree used 290 to 420 MB.

This grows linearly with the number of servers. Nothing here limits a single host to a few servers; the game servers' own memory and CPU do.

Load that grows with players

  • Events: every RCON event passes through the bus. Most go only to StateTracker; chat and joins also reach automod and the command router; kills (one per death, frequent at 100+ players) reach StateTracker alone unless the event log is on.
  • Automod: one normalisation and one pass of the compiled patterns per chat line, on at most 600 characters, plus one SQLite count when a word matches; one SQLite lookup per join for an active mute; and a name check per new player and name every 5 s, kept until a list changes.
  • SQLite: one upsert per join and one insert per moderation action. At the live server's scale (128 players, join and leave churn after every game) this is a few writes per second at peak.
  • Watchdog: at most 120 frame samples and 500 connection and join timestamps per server, evaluated once a minute.

At the live server's scale

The live server runs 128 players on a 2 GB map (Hugegrass) and spends full games at about a third of its tick rate (plans/crash-analysis-live-server.md). That load is the game's, not Huragok's; the Superintendent's job there is to not restart it for being slow, which is why the frame cases only watch.

Disk

  • huragok.log: at most 30 MB (5 MB × 6 files). window.log: at most 10 MB. launcher.log: appended without limit, but rarely written.
  • console-<slug>.log: unbounded (Known issues).
  • The database: about 50 KB on the test root; it grows with players seen and actions, with no cleanup.
  • records/previous-program/: one set of program copies (about 25 MB each) per install or swap; records/previous-<V>/: one per self-update. Nothing removes them by itself; Clean up (U) offers every set but the newest, and every Huragok backup but the newest by version and the one last-update.json names.
  • records/program-download/: the last release downloaded for a fallback install (about 25 MB); the next download replaces it.
  • Also offered by Clean up: *.exe.old files, Workshop items' old copies in .huragok-workshop-previous/ (half-fetched -failed ones always), SteamCMD's copies of items no server lists (data/workshop-cache), and content-unused-* folders.

Smaller findings

Found while checking this document against the code after the audit; each is small and none blocks the launch.

  • The dashboard's health reasons change only when the level changes; a new case at the same level is in the log only.
  • The budget counts every automatic countdown begun, one cancelled with K included, and a manual restart right after a budget FAULTED can fault the server again within the hour.
  • start.cmd update waits 300 s (--wait), while an installed update may wait up to 30 minutes for restarts in progress: the command can say "Not done" while Huragok is only waiting. An update installed with Huragok not running has no put-back if the new version then fails.
  • U can miss self-updating servers. When every copy run by servers with auto_update off is already current, the install stops there, so self-updating servers still behind aren't taken over by U. The bulk install also always includes the root's copy, even when only self-updating servers run it.
  • A rolled-back install or a failed swap can leave an empty set in records/previous-program/, which Clean up may keep as "the newest" while offering the real newest.
  • The preparing phase isn't one of the Superintendent's faces: a server installing a job before its start shows "every server is stopped".
  • automod: a name with no letters or digits (★★) is written to names.txt by !strike … name but matches nothing; its replies say "!" whatever the prefix; cooldown_seconds and split_seconds aren't type-checked.
  • Setup: a playlist whose vote_seconds or a weight isn't a number stops the screen that lists it; rename checks name clashes only against the servers in this run, where new counts disabled and left-out ones; D's [master] port isn't checked against the servers' ports; N asks for 1 to 127 players even for a co-op package, which then fails at the end.
  • Names in messages: HURAGOK_LAUNCHER's fallback is "huragok" in some messages and start.cmd / ./start.sh in others, and the Docker image doesn't set it.
  • deploy.ps1 treats a lock as live by its process number alone.

Decisions the fixes made

  • Vergil: a match with more digits than letters isn't a hit ("455 kills" no longer hits a three-letter insult, but "a55" isn't caught either); !ban <a name Vergil has seen> bans that player's ID while they're away; moderators on the relay see no addresses at all (the server's own included) and no IPs typed in chat.
  • D refuses (rather than warns about) a setting the server's program is too old for.
  • Playlists write the character-set choice as a number, the one option whose label differs by version.
  • A Workshop update that fails is tried after up to two more games (one more restart each), then waits for U.
  • A program swap that keeps failing (an antivirus) is tried after 1, 4 and 12 hours, then waits for U; a copy that doesn't answer --version isn't counted as behind.
  • A stop that can't end the process leaves the server running and says so, rather than pretending (wanted is stopped).
  • An installed self-update waits up to 30 minutes for restarts in progress before Huragok relaunches; a manual update waits the same way.
  • Minimums of 30 s for hang_seconds and ready_seconds.
  • The A console still closes after two minutes without typing, even while events arrive.
  • 0.2.1 hosts reinstall: no bridge across the rename.

Part 2: Interfaces and data formats

This part is the contract at the edges: every message, file and table Huragok reads or writes, as of 19 October 2026 against server program v0.9.18 (and v0.9.20 where it differs). Part 1 explains the behaviour; this part is for anyone changing code that touches these formats. The server's side of the RCON protocol is documented in its own RCON.md.

RCON client protocol

Huragok holds one WebSocket connection per server and speaks the server's JSON protocol, version 1 (rcon.py).

Connecting

Signing in

{"type": "auth", "password": "…", "host_key": "<contents of data/<slug>/rcon-host.key>"}

{"type": "auth", "ok": true, "protocol": 1, "server": "LG Test Server", "version": "0.9.18"}
  • host_key is sent when [rcon] use_host_key is on and the key file exists. It puts Huragok on the spot kept for the server's own machine.
  • After ok, the key file is read again. If it changed (the server restarted during the sign-in), the connection is closed and made again, so Huragok does not sit on a normal spot.
  • If there was no key at sign-in, the file is checked every 2 s for up to 120 s; when it appears, Huragok reconnects onto the kept spot.
  • ok: false with full: true raises RconFull: retry in 30 s. Any other ok: false raises RconAuthError: the client remembers the refused password, logs an error, emits rcon.auth_failed (error, lockout) and waits: it signs in again when instance.json gives a different password (looked at every 5 s), once when the server starts again (while fewer than 2 refusals fall in 10 minutes), or after 10 minutes. A refusal whose words speak of a lockout, or the server's own lockout line in server.log, makes it a lockout ("this machine is locked out of the console for N minutes"). A good sign-in clears it ("RCON took the password again; the console is back").
  • A protocol other than 1 is logged as a warning and the session carries on.

Commands and replies

{"type": "command", "id": 8, "command": "ban", "args": ["<player ID>", "1d", "KEEP IT CLEAN! That isn't allowed here…"], "by": "Vergil"}

{"type": "reply", "id": 8, "ok": true, "text": "Banned …", "data": null}
  • Ids come from a counter per client (not reset on a reconnect). A reply is matched to its pending command by id. A command over 16 KiB isn't sent: "command too long for one RCON message (16 KiB)".
  • by is set for moderation actions, ! commands, relay commands and console lines when a name was given (not for say, countdown warnings or M), so players read who acted and the server's ban list records <name> (RCON).
  • Errors: RconUnavailable (not connected: not sent; or the connection dropped while waiting: it may have run), RconTimeout (no reply within command_timeout: may have run, never resent).
  • one_shot() signs in (no host key), runs one command (id 1) and signs out on a normal spot. start.cmd rcon and say use it only when Huragok isn't running; otherwise they go through the mailbox and the shared connection.

Server-side limits worth knowing

A client has 10 s to sign in. Five wrong passwords from one address in 10 minutes refuse that address, right password or not. At most 4 tools are signed in, plus the kept spot; at most 16 connections may be open, 4 per address. A client more than 256 events behind gets lagged and continues with the newest.

Relay protocols

When [relay] enabled = true, Huragok serves each server's console to remote moderators on two extra ports (relay.py, Vergil's). Both forward commands over Huragok's own RCON connection.

Endpoint Port Protocol Events
WebSocket console game port + port_offset (1000): 49176 becomes 50176 The server's own WebSocket protocol, version 1, subprotocol reclaimer-rcon, up to 1 MiB per message Yes
Source RCON game port + source_port_offset (2000): 49176 becomes 51176; 0 switches it off Valve's Source RCON No

Both listen on [relay] address (default 127.0.0.1). A port that cannot be bound is logged as an error, and only that server's relay is off.

WebSocket sign-in

The first message must arrive within 10 s and be an auth:

{"type": "auth", "password": "<this moderator's relay password>"}

{"type": "auth", "ok": true, "protocol": 1, "server": "LG Test Server", "version": "0.9.18", "relay": "Superintendent", "role": "moderator"}

relay is the top-level name setting ("Superintendent" as the first start writes it). The password picks the [[relay.user]], which is why passwords must be unique. A wrong one gets {"type": "auth", "ok": false, "error": "Wrong password."}. After 5 wrong passwords in 10 minutes, the address is refused for the rest of that window ("Too many wrong passwords from your address; try again in ten minutes."); unlike the server, a right password does not clear the count. There is no limit on open connections.

WebSocket commands and events

  • A {"type": "command", "id", "command", "args"} message gets a reply with the same id, ok, text and, when the server gave one, data. A by sent by the client is ignored: the relay sets by to the signed-in user's name.
  • A command the role does not allow is answered ok: false with "'<word>' needs the <role> role; you're <role>. Ask the host to change commands.toml.", and never reaches the server; one in [off] with "'<word>' is switched off in commands.toml ([off]), for everyone."
  • Refused before anything else: a line with a new line, tab or other control character ("One command per message, on one line: new lines, tabs and other control characters can't go through."); with args, a command that isn't one word ("With args, command is the command's name alone, like {"command": "kick", "args": ["#3"]}."); a blank word in args ("An empty or blank word in args can't go through; leave it out."). With its console away: "<server>'s console isn't connected right now." A game command on an ODST server gets Huragok's own ODST refusal.
  • Each forwarded command waits at most 15 s for the server's reply.
  • Messages that are not JSON or not commands get {"type": "error", "text": …}.
  • Every rcon.* event for that server is forwarded as the server would send it, except connected, full, auth_failed and unknown. lagged passes through. A dropped upstream connection becomes {"type": "event", "event": "control", "action": "relay", "ok": false, …}. For users below admin, replies and events lose every ip, address, device and fingerprint key (at any depth) and devices' ids, and IPv4 and IPv6 addresses (with a range or a port) and device <64 hex> in text read "(hidden)".

Source RCON

  • The first packet must be an auth packet (type 3) within 10 s. As Source servers do, the relay answers with an empty response (type 0), then the result: type 2 with the request's id on success, or id -1 with the reason on failure.
  • An exec packet (type 2) runs the command through the same role check; the reply text is split into packets of at most 4,096 characters, each with the request's id.
  • An empty response packet (type 0) from the client is echoed back, which is how clients find the end of a split reply.
  • Packets outside 10 to 4,106 bytes end the connection.

records/huragok.pid (the lock)

{"pid": 30208, "create_time": 1792190000.12, "version": "0.4.0", "launcher": true}

The start loop writes it with "launcher": true; the child takes it over ("launched_by": the start loop's own) and hands it back as it exits, so the lock is held across a restart or a relaunch. It is written to a temporary file (huragok.pid.<pid>-<n>.tmp) and hard-linked into place, so two starters at the same instant can't both win (O_CREAT | O_EXCL where hard links don't work). A lock whose process is gone (pid and start time checked) is renamed aside (huragok.pid.<pid>.stale), read again in case it changed meanwhile, and only then removed; a half-written lock under 10 s old is waited on. The name is fixed, not a setting; 0.2.1 and earlier wrote supervisor.pid, and a live one counts as running. status reads a lock held by the start loop alone as "Huragok is starting again".

Database schema

One SQLite file, records/huragok.sqlite3 by default (the database setting; a 0.2.1 settings.toml names records/supervisor.sqlite3), in WAL mode with autocommit. Times are Unix seconds (REAL); player IDs are stored lowercase. A casefold() SQL function is registered, so seen names are found in any case (Élodie, ÉLODIE; Straße).

Migrations

schema_versions (owner TEXT PRIMARY KEY, version INTEGER NOT NULL) records how many steps each owner has applied: core, then each part by name. Storage.migrate(owner, steps) applies the missing steps in a transaction each. A released step is never edited; changes are new steps appended.

Automod (steps 1 and 2)

CREATE TABLE automod_strikes (
    number INTEGER PRIMARY KEY, time REAL NOT NULL, server TEXT, player_id TEXT NOT NULL,
    player_name TEXT, rule TEXT NOT NULL, grp TEXT NOT NULL, source TEXT NOT NULL, evidence TEXT,
    by TEXT NOT NULL, action TEXT NOT NULL, duration TEXT, expires REAL, dry_run INTEGER NOT NULL,
    ok INTEGER NOT NULL, pardoned REAL, pardoned_by TEXT);
CREATE INDEX automod_strikes_player ON automod_strikes (player_id, grp, time);
-- step 2 (0.3.0): a mute someone lifted
ALTER TABLE automod_strikes ADD COLUMN lifted REAL;
ALTER TABLE automod_strikes ADD COLUMN lifted_by TEXT;
  • rule and grp both hold the rule's name; the count for escalation is by grp.
  • source is chat or manual (name on rows from before 0.3.0); action is kick, mute or ban; duration like 1d, empty for a plain kick, a mute for good or a permanent ban; expires is when a timed step ends.
  • Active mute: action = 'mute', pardoned and lifted empty, the current dry_run, and expires empty or still ahead; the longest is the one sent again on a join. ok is not part of it: a mute the server refused is still sent at the next join.
  • Active strikes: pardoned IS NULL, time within forget_after_days when set, and dry_run equal to the current dry-run setting. That last condition is why turning dry run off starts every count at zero.
  • !pardonplayer sets pardoned and pardoned_by rather than deleting rows.
  • Rows are keyed to the rule's name, which is why an unnamed line (rule2 by position) is warned about: a line added above it would move its strikes.

Host file formats

commands.toml

prefix = "!"            # anything but "/" (the game keeps / lines), no spaces
cooldown_seconds = 3    # per player and command; admins and owners wait for nothing

[everyone]
commands = ["help", "strikes"]

[member]
players = ["<64 hex characters>"]
commands = []

[moderator]
players = ["<64 hex characters>"]
commands = ["players", "whois", "warn", "mute", "unmute", "kick", "pardon", "strike", "health"]

[admin]                 # the server's own admins; no players list allowed here
commands = ["ban", "unban", "say", "map"]

[owner]
players = ["<64 hex characters>"]
commands = ["admin", "reload"]

[off]
commands = []
  • Only prefix, cooldown_seconds, the five role sections ([everyone], [member], [moderator], [admin], [owner]) and [off] are allowed; each section only players and commands, and players only in [member], [moderator] and [owner].
  • A command sits in the lowest role allowed to use it; a command in no list keeps its default role. Commands may be written with the prefix and in any case. Errors: an unknown command name, a command listed under two roles, an alias, help in [off], a player ID that isn't 64 hexadecimal characters, a prefix that is empty, starts with / or has a space.
  • Looked at every 2 s. A file with a mistake keeps the previous version in force; one that is briefly missing or empty (an editor saving it) keeps the roles in force until it has something in it.
  • The first start writes the file with every command under its default role and its help text as a comment.

automod.txt

# words                       | kicks       | mutes         | ban | name
badword, otherword*, -okword  | 1h          | 1, 1d, 7d     | 3   | slurs
rudeword                      |             | 0, 1d, 3d, 7d |     | rude
kickword
Field Rules
words Comma-separated. word matches whole words and plurals; word* also the start of longer words; *word* anywhere; -word is an exception for that line
kicks Optional; each a number and s, m, h, d or w; the last repeats until the mutes. Empty: the server's own kick (10, 30, 60, then 120 minutes). A time past the start of the mutes kicks, then mutes once the kick ends. At most one time per strike before the ban
mutes Optional. A number, 0 to 20: the strikes before the mutes start; then at least one time, in order, the last repeating; perm (last only) mutes for good. Empty: never muted. At most one time per mute before the ban; the mutes must start before the ban
ban Optional, 0 to 20. Strikes before a permanent ban. Empty: never banned
name Optional; one short word (letters, digits, -, _), not name. What players read and what !strike takes. Unnamed lines become rule1, rule2… Two lines may not share a name

Blank lines and lines starting with # are ignored. The file may be UTF-8, with or without a byte-order mark, or UTF-16 with one (Notepad's "Unicode"); anything else (ANSI, UTF-16 without a byte-order mark) is refused with "save it as UTF-8". A word that is nothing once normalised (only invisible characters or accents) is refused, naming the line. Edits are picked up within 5 s; a line with a mistake, a file held by an editor, or a deleted file keeps the previous rules in force. A line in four parts whose last part is a name is the 0.2 layout, words | timers | chances | name, read as words | timers | | chances | name.

names.txt

# banned 2026-10-18 by Alice: offensive
Bravo
*badname*

One banned name per line; blank lines and lines starting with # are ignored, and a missing file is no banned names. Each name is matched like a word of automod.txt: disguises caught, whole words inside a longer name, * at either end to widen. !strike <player> name appends the player's name (without * at its ends or a leading #) under a # banned line; !unbanname removes every line naming it (compared normalised, spaces aside: case, accents, lookalike letters and invisible characters don't matter, digit stand-ins do), with the # banned line just above. Same encodings as automod.txt; an entry that is nothing once normalised is skipped. Edits are picked up within 5 s.

Exit codes

Code Meaning
0 Done; or the window was closed (Q, close, stop)
1 It didn't work: a command failed (an update, a stop or restart through Huragok, close timing out, say or rcon refused, problems found by check, init over an existing file); an unhandled crash (which the start loop starts again); the launchers' Python missing or setup failing
2 A settings problem; or a name it doesn't know, or wrong usage (an unknown server for stop, say, watch or rcon with Huragok not running; rcon with no command; several servers and no --server; argparse errors)
3 First start: the host files were written; look them over and start again
4 start: Huragok is already running from this folder (without a window)
5 status: nothing is running
10 Child to start loop: a new version is installed, start it (never seen by the host)
Other A crash; the start loop names it ("exit code 0xC0000005", "ended by signal 9") and starts Huragok again

0, 3 and 4 end the start loop as they are; 2 ends it too, except with --no-menu, where it waits and tries again. With --hold (what a double-click uses), any code other than 0 and 10 keeps the window open until Enter. --help ends with the exit codes 0 to 5. dedicated passes on the program's own code (124 after a timeout, 130 when stopped); the _ctrl-break helper exits 0 when the event was sent, 2 when it couldn't attach, 3 when the event failed.

A server is named by its name, its folder slug or its number (2 or #2), the same with or without Huragok running.
